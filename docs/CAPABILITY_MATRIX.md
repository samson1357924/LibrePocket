# LibrePocket 能力與接線狀態

> **Current snapshot**：依 `0185935` 核對（2026-10-16，S1–S7＋R27＋R28-1）。本文件不把規格列出的能力當成已可用功能。
>
> - **範圍：** built-in tools、provider adapters、三個 flavor 的 source/manifest 邊界。
> - **Owner role：** app/runtime 維護者；未指派個人。
> - **Source of truth：** `ToolRegistry`/`ToolDef`, production composition, flavor source sets, dependencies, and manifests; CI artifact gates provide only the checks they explicitly run.
> - **更新觸發：** 工具實際接線/readiness、provider adapter、manifest、flavor dependency 或 artifact gate 改變時。

## 狀態詞彙

- **Declared**：有型別、schema、描述或規格列項。
- **Implemented**：有 production implementation；測試 fake 不算。
- **Wired**：從 production app entry point 接到實際 dispatcher/副作用。
- **Verified**：有對應正向與負向測試；若需 Android 行為，須有指定裝置/API 的實跑證據。

單一狀態不自動代表下一狀態。圖示、投影結果、權限列、dependency 或 service 宣告均不是 end-to-end 功能證明。

## Target：工具接線前的驗收

每個工具需單獨列明 flavor、使用的實體資源、權限要求、使用者確認、fresh policy evaluation、dispatcher/executor、取消與錯誤語義、持久化/審計路徑，以及正向與拒絕控制測試。未完成上述驗收時保持 `executionReady=false`。不要把 41 項一次改為 ready。

### MCP 啟用／接線 gate 清單

MCP 目前 declared＋implemented、未接線、未驗證（僅 JVM）。啟用／接線前（即接線 PR 內）必須完成：

- **Production 接線**：`McpServer`／`McpScope` 接上 dispatcher/executor（MCP 目前零 production import，見 `scripts/docs_claim_check.sh` zero-wiring 檢查——五面 fail-closed：① AndroidManifest 註冊（text grep＋XML）、② Gradle manifest 注入（placeholders／srcFile／namespace／applicationId／gradle.properties）、③ 包內出站 import 白名單／FQN、④ 全模組 package 分類的包外引用、⑤ discovery／classification fail-closed，D-01）。
- **逐工具 `executionReady` 翻轉＋完整驗收**：每個工具按上方驗收項目（flavor、實體資源、權限、使用者確認、fresh policy evaluation、dispatcher/executor、取消與錯誤語義、持久化/審計路徑、正向＋拒絕控制測試）個別完成後才翻轉；不得一次全開。
- **取消與副作用邊界驗證**：MCP 呼叫走同一投影＋確認閘——一律 WRITE（MCP 子集無 sideEffect 宣告、`check` 不收呼叫端 sideEffect 參數），在 `callTool` 前經 `McpScope.check` 確認（`McpGate.NeedConfirm` 攜結構化授權識別 `switchKey`；`toolName` 僅展示，不得以展示字串回送授權對象——C-04）；取消語義與內建工具同等要求。**明確前置（security P3）**：`McpServer.callTool` 本身**不**呼叫 `McpScope.check`（已於其 KDoc 註明）；接線 dispatcher 必須先以結構化 `switchKey` 執行 `McpScope.check` 並綁定該確認，之後才呼叫 `callTool`；不得以展示名 `ToolDef.name` 回送或比對授權對象。
- **單一投影真相（已在包內強制，接線不得回退）**：`McpScope.check`／`canExecute` 不收呼叫端 `Projection`，每次呼叫以傳入 `McpServerConfig`＋`ProjectionContext` 內部重投影（`project()`）——停用前的舊投影／他服的舊投影無法再被帶入放行（舊版信任呼叫端投影、不重查 `config.enabled`，`check(offCfg,…, project(onCfg,…))` 會 Allowed；現為 Denied）。接線 PR 不得改回「呼叫端自備 Projection」的 API 形狀（對比內建 `PrivilegeGate.check` 仍是呼叫端自備投影——MCP 這條路刻意收得更嚴）。
- **`switchKey` 跨服鍵碰撞已收斂（C-04，Stage5 P3 修復）**：開關鍵改形狀分離 `switchKey = mcp.<serverId 的 UTF-16 code units 數（String.length）>|<serverId>|<toolName>`——長度前綴＋`|` 定界使任意 `(serverId, toolName)` 皆單射（`switchKey("a.b","c") = mcp.3|a.b|c` ≠ `switchKey("a","b.c") = mcp.1|a|b.c`），不同伺服器不再可能互相覆寫；`mcp.` 前綴使開關鍵永不可能是合法 bare 名（`McpScope.requireBareToolName` 必拒，fail-closed）。`McpGate.NeedConfirm` 同步攜帶 `switchKey` 作授權識別（`toolName` 僅展示），接線不得以展示名回送。**刻意保留** `ToolDef.name = mcp.<id>.<tool>` 展示字串契約不變（改它屬 breaking），該字串自身在含 `.` 的 id 上的 `.` 歧義屬展示層殘餘（授權不經它），以 `McpScope` KDoc 誠實揭露而非靜默修復。接線前若要收斂展示層歧義，須 breaking 改 `ToolDef.name` 形狀。
- **`toToolDef` 主開關在內建投影路徑的殘餘覆寫**：`toToolDef(config,…)` 的 `switchDefault` 已接 `config.isToolEnabled`（停用伺服器／停用工具 → 預設 context 的內建投影 UNAVAILABLE+USER_DISABLED；`executionReady=false` 雙閘不變），但內建 `ToolDef.project` 只看 `ProjectionContext.userSwitches`、看不到 `McpServerConfig`——ctx 明寫 `userSwitches[McpScope.switchKey(id, tool)]=true`（結構化授權鍵；展示名 `ToolDef.name=mcp.<id>.<tool>` 不參與開關查找，C-04）仍可把停用伺服器的 ToolDef 翻回 NATIVE（包內無法表達「無條件主開關」：內建 annotations 沒有不可覆寫的停用位）。MCP 自己的 `project`／`check`／`canExecute` 一律以 config 重查、不受此影響；接線 PR 須以 config 重驗或收斂此分歧（見 `McpScope.toToolDef` KDoc）。另 `switchDefault` 是**建構當下的 config 快照**：config 變更（含伺服器停用）後 ToolDef 必須以新 config 重建，否則內建路徑落後於當下 config（MCP 自己的路徑以 config 重查，不受影響）。
- **Key 重綁確認**：keyId↔baseUrl 無自動綁定；接線 PR 須加入 rebind 確認，URL 變更不得靜默沿用舊 key（見 THREAT_MODEL Target「Credential 綁定 endpoint」與 S4-C）。
